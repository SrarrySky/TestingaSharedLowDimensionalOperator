# 🔁 Reproducibility and release layout

This repository is the code companion for:

> **Testing a Shared Low-Dimensional Operator Representation for Time-Varying Financial Dynamics**

This is the experiment code for the paper by Jiyu Mo and Dongyang Kuang, prepared for an ICMLC 2027 submission. The implementation covers synthetic, geometry, baseline, and out-of-sample analyses. No proceedings DOI or pagination is asserted here. This page describes the public repository without depending on the manuscript working directory.

## What is included

- `src/`: reusable model, filtering, causal-screening, baseline, geometry, and evaluation code.
- `config/`: versioned experiment specifications. Each experiment should be run with an explicit output directory.
- `scripts/`: orchestration and figure-generation entry points. Names use lowercase `snake_case`.
- `tests/`: unit, theory, leakage, and pipeline-contract tests.
- `docs/PAPER_TO_CODE.md`: method-to-implementation and evidence map.
- `paper_supplement/MATHEMATICAL_DERIVATIONS.md`: complete derivations for the paper's propositions, corollary, estimation equations, and diagnostics.
- `paper_supplement/ROBUSTNESS_AND_UNCERTAINTY_RESULTS.md`: the numerical post-acceptance robustness and uncertainty record.
- The post-acceptance runbook is consolidated below; those analyses remain distinct from the published experiment.

## What is intentionally not included

Generated run directories, retry artifacts, logs, caches, IDE metadata, and local virtual environments are not release materials. They are ignored by Git and should be regenerated locally under `outputs/`.

Raw and processed financial data are also excluded because their redistribution depends on the data provider's terms. The manuscript working directory is not part of the public release. Place authorized files under `data/raw/` and create the processed dataset with the documented pipeline. Locally generated outputs must be checked against their own manifests and configurations.

## Minimal verification

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev,hmm]"
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m cli theory-checks
```

The test suite checks implementation contracts. It does not regenerate the financial-data experiment. For a credential-free integration check, run:

```powershell
.\.venv\Scripts\python.exe -m cli synthetic --scenario shared_low_rank --output outputs/checkpoints/synthetic_demo.npz
```

For the full experiment, obtain authorized data, then run `dlcssm download --config config/data.yaml` and `dlcssm prepare --config config/data.yaml`. The staged runner is `scripts/run_main.py` with `config/main_runner.json`. Inspect its CLI options with `python scripts/run_main.py --help` and use a new output directory. The runner requires all configured stages, including real-data inputs and resource-intensive geometry checks. Its stage manifest and ledger provide completion evidence; a successful unit test is not a substitute.

The post-acceptance runbook gives the exact six-worker commands and verification criteria for the S5 ten-seed and OOS block-length experiments. Its paths under `outputs/post_supplement/` are local generated artifacts, not bundled evidence. For the split, target, and paper mapping, see [Methods](METHODS.md), [Data and provenance](../data/README.md), and [Paper-to-code](PAPER_TO_CODE.md). For the mathematical proofs and calculations, see [Mathematical derivations](../paper_supplement/MATHEMATICAL_DERIVATIONS.md); for the numerical findings generated by the supplementary runbook, see [Robustness and uncertainty results](../paper_supplement/ROBUSTNESS_AND_UNCERTAINTY_RESULTS.md).

## Consolidated release and execution reference

The following sections consolidate installation, release boundaries, troubleshooting, and post-acceptance run procedures.

## Installation and tested environment

This page documents the supported installation paths for release `0.1.0`. The package metadata in [`pyproject.toml`](../pyproject.toml) is authoritative for Python and dependency constraints.

### Supported runtime

- Python: 3.10, 3.11, or 3.12.
- Primary implementation: NumPy/SciPy on CPU.
- Tested continuous-integration platform: Ubuntu through GitHub Actions.
- Local development has also used Windows PowerShell; identical floating-point values across operating systems or BLAS implementations are not guaranteed.

No GPU is required. Full real-data runtime and peak-memory measurements are not claimed because they depend on the licensed dataset, selected stages, worker count, and posterior-predictive draw count.

### Editable installation

From the repository root, create an isolated environment and install the package. The commands below use Windows PowerShell:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -e ".[dev,hmm]"
.\.venv\Scripts\python.exe -m pytest -q
```

For a POSIX shell:

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -e ".[dev,hmm]"
.venv/bin/python -m pytest -q
```

Install `.[causal]` only when running the optional Tigramite/LPCMCI branch. The primary lagged-Lasso support screen does not require that dependency.

### Verification levels

The following checks answer different questions:

```powershell
## Static checks and unit/integration tests.
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m pytest -q

## Credential-free mathematical consistency checks.
.\.venv\Scripts\dlcssm.exe theory-checks

## Small orchestration smoke run; not a paper-result reproduction.
.\.venv\Scripts\python.exe -B scripts/run_main.py `
  --config config/main_runner_smoke.json `
  --output outputs/main_smoke `
  --allow-incomplete
```

A passing test suite verifies the encoded contracts only. It does not validate the empirical conclusions or regenerate the restricted-data experiment.

### Dependency provenance

`pyproject.toml` contains the canonical direct requirements and optional dependency groups. `requirements.txt` is a convenience list and is not a fully locked environment. For an archival paper release, export the resolved package versions and record the Python, operating-system, BLAS/LAPACK, and hardware information alongside the run manifest.

### Credentials

Real-data acquisition requires a user-provided Tushare token:

```powershell
$env:TUSHARE_TOKEN = "<token>"
```

Do not place credentials in configuration files, logs, issue reports, or commits. See [`data/README.md`](../data/README.md) for access and provenance.

## Open-source release scope

This page defines the intended public source artifact for release `0.1.0`.

### Included

- `src/`: reusable implementation.
- `scripts/`: experiment, verification, aggregation, and plotting entry points.
- `config/`: versioned scientific and orchestration settings.
- `tests/`: behavioral, leakage, numerical, and theory checks.
- `docs/`, `README.md`, and `data/README.md`: scientific and operational documentation.
- `pyproject.toml`, `requirements.txt`, `Makefile`, `.env.example`, and CI configuration.
- `LICENSE`, `CITATION.cff`, `CONTRIBUTING.md`, `CHANGELOG.md`, and third-party notices.
- `SECURITY.md` and `CODE_OF_CONDUCT.md`.

### Excluded

- `outputs/`: generated checkpoints, predictions, tables, figures, ledgers, logs, and local run manifests.
- `Write/`: manuscript sources, compiled paper files, reviewer-response material, and author working notes.
- Raw, interim, and processed third-party financial data except placeholder and documentation files explicitly approved for redistribution.
- Virtual environments, IDE metadata, caches, coverage files, temporary files, screenshots, local logs, and credentials.

Exclusion from the source release does not imply that generated evidence is unimportant. Every reported result should remain reproducible from a released configuration and should be archived separately when licensing permits.

### Pre-release boundary audit

Run the following from the release candidate branch:

```powershell
git status --short
git ls-files outputs Write data/raw data/interim data/processed .idea
git grep -n -I -E "(TUSHARE_TOKEN|api[_-]?key|secret|password)"
```

Review every match. `.gitignore` affects only untracked files; it does not remove an already tracked file or erase repository history. If restricted material was committed previously, prepare a clean public release branch or rewrite history using a reviewed backup and an explicit credential-rotation plan. Do not perform history rewriting as an incidental cleanup step.

### Result and manuscript references

Public documentation may describe expected generated paths under `outputs/` and may refer to paper sections, figures, or tables. Such references do not make the local output directory or manuscript working tree part of the open-source artifact.

## Troubleshooting

The remedies below describe known operational causes; they do not suppress failed scientific checks.

### `No module named cli`

Cause: the package is not installed and `src/` is not on Python's import path.

Remedy: run `python -m pip install -e ".[dev,hmm]"` from the repository root, then use `dlcssm --help`. Avoid modifying `PYTHONPATH` in release instructions when an editable installation is available.

### Missing Tushare token or endpoint failure

Set `TUSHARE_TOKEN` in the process environment and confirm that the account has permission for every endpoint enabled in `config/data.yaml`. Do not place the token in a committed file. Provider rate limits and permissions are external conditions; retrying cannot grant unavailable access.

### Optional dependency unavailable

Install `.[hmm]` for automatic HMM baselines and `.[causal]` for Tigramite-based LPCMCI/PCMCI+ sensitivity branches. The runner records unsupported cells rather than substituting another estimator.

### A run directory already exists

Use a new output directory for a scientifically changed configuration. Use `--resume` only to reuse verified successful cells from the same run identity. Do not merge files manually across run directories.

### Non-positive-definite covariance or failed PSD solve

Check input finiteness, scaling, sample size, state dimension, and covariance regularization. The implementation applies bounded diagonal jitter; failure after those attempts indicates that the requested fit is not numerically valid. Do not increase tolerances merely to obtain a successful status without recording and justifying the change.

### Nonconvergence or incomplete publication run

Inspect the stage ledger, cell diagnostics, likelihood trace, and `coverage.json`. `--allow-incomplete` changes orchestration exit behavior but does not turn an incomplete run into publication evidence. In publication mode every required stage must succeed.

### Different numerical values on another machine

Record Python and package versions, operating system, BLAS/LAPACK backend, thread counts, random seeds, and configuration hashes. Compare using the metric-specific tolerances or verification scripts rather than assuming bitwise identity.

### Raw or processed data appear in Git status

The data directories are ignored for new files, but ignore rules do not remove files already tracked by Git. Before a public release, inspect `git ls-files data` and remove restricted tracked artifacts from the release branch only after confirming the intended data-distribution policy.

## 🧪 Post-acceptance supplement experiments

This runbook covers the post-acceptance S5 seed extension, archived S5 recovery summary, and fixed-fit OOS block-length sensitivity analysis. It does not update the manuscript and does not reuse prior synthetic cells.

These experiments were completed in the local research workspace: the S5 verifier recorded 70 successful cells and matching current source, and the block-sensitivity combiner verified fixed predictions, selected alpha and point estimates across block lengths 10, 20 and 40. The generated directories under `outputs/` are not distributed with the public repository. The commands below allow an authorized user to produce their own evidence. They represent later post-acceptance analysis, not a claim that the published paper contains it.

All commands below are PowerShell commands run from the repository root. Every output directory must be new or empty. The common output root is:

```text
outputs/post_supplement
```

### 1. Configure six-thread execution

Set the numerical-library and joblib thread limits once in the current PowerShell session:

```powershell
$env:OMP_NUM_THREADS = "6"
$env:MKL_NUM_THREADS = "6"
$env:OPENBLAS_NUM_THREADS = "6"
$env:NUMEXPR_NUM_THREADS = "6"
$env:LOKY_MAX_CPU_COUNT = "6"
```

The synthetic benchmark additionally uses `--jobs 6`. DLC validation and support discovery use six workers with one numerical inner thread per worker, which avoids nested 6-by-6 oversubscription. The OOS bootstrap is vectorized and has no separate `--jobs` option. The verification and summary commands are lightweight read/aggregation tasks.

### 2. Preflight checks

Inspect the working tree before starting:

```powershell
git status --short
```

The synthetic manifest records the complete current `src/` hash inventory. Commit or otherwise freeze the source before Task A, and do not change `src/` between the benchmark and its `--require-current-source` verification.

Optionally run the complete test suite:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

#### Re-running after an interrupted stage

Use a new output root and update the paths in the commands below if an earlier run is partial or if scientific inputs have changed. Preserve the earlier directory and its manifest for diagnosis. A fresh public checkout has no pre-existing Task B artifact; the following step requires a locally generated `outputs/s5_recovery_control/summary.json`.

### 3. Task B: summarize the archived S5 recovery controls

This command summarizes a locally generated recovery-control file and performs no model fitting. The original local run contained 12 records; a fresh run must be checked against its own manifest:

```powershell
.\.venv\Scripts\python.exe scripts/summarize_s5_recovery.py `
  --input outputs/s5_recovery_control/summary.json `
  --output outputs/post_supplement/B_s5_recovery_summary
```

Expected outputs:

```text
outputs/post_supplement/B_s5_recovery_summary/
├── s5_recovery_rows.csv
├── s5_recovery_summary.csv
└── manifest.json
```

The exporter renames the archived `em_iterations` field to `objective_history_length`, because it includes the initial objective value.

### 4. Task C: fixed-fit OOS block-length sensitivity

These commands reuse the saved design matrices. They do not refit DLC-SSM, HMM, the baseline models, or propagation features. The scorer requires the current `main-m0-m5-pathwise-v2` contract and verifies every declared M0--M5 feature before scoring.

The original local run used the exported design at `outputs/main_mid_run/oos_design`. Produce a compatible design before running this scoring-only step, then adjust `--design-dir` to its location. The scorer requires the current declared M0--M5 specification.

#### Block length 10

```powershell
.\.venv\Scripts\python.exe -m oos.oos_experiment `
  --design-dir outputs/main_mid_run/oos_design `
  --config config/oos_predictive_cm050_block10.json `
  --output outputs/post_supplement/C_oos_block_sensitivity/block_10
```

#### Block length 20

```powershell
.\.venv\Scripts\python.exe -m oos.oos_experiment `
  --design-dir outputs/main_mid_run/oos_design `
  --config config/oos_predictive_cm050_block20.json `
  --output outputs/post_supplement/C_oos_block_sensitivity/block_20
```

#### Block length 40

```powershell
.\.venv\Scripts\python.exe -m oos.oos_experiment `
  --design-dir outputs/main_mid_run/oos_design `
  --config config/oos_predictive_cm050_block40.json `
  --output outputs/post_supplement/C_oos_block_sensitivity/block_40
```

#### Combine and verify the three runs

```powershell
.\.venv\Scripts\python.exe scripts/summarize_oos_block_sensitivity.py `
  --block10 outputs/post_supplement/C_oos_block_sensitivity/block_10 `
  --block20 outputs/post_supplement/C_oos_block_sensitivity/block_20 `
  --block40 outputs/post_supplement/C_oos_block_sensitivity/block_40 `
  --output outputs/post_supplement/C_oos_block_sensitivity/combined
```

The combiner requires identical selected alphas, fitted specifications, predictions, Test metrics, point estimates, and input hashes. Only the four bootstrap interval columns may differ. Expected outputs:

```text
outputs/post_supplement/C_oos_block_sensitivity/combined/
├── block_sensitivity.csv
└── manifest.json
```

### 5. Task A: run the fresh S5 ten-seed benchmark

This is the only heavy supplementary computation. Do not add `--reuse-from`.

```powershell
.\.venv\Scripts\python.exe -m experiments.synthetic_benchmark `
  --config config/synthetic_main_s5_10seeds.json `
  --output outputs/post_supplement/A_s5_10seeds `
  --jobs 6
```

Failures must remain in the ledger; do not replace a failed seed.

#### Verify Task A

Run this before changing any source file:

```powershell
.\.venv\Scripts\python.exe scripts/verify_synthetic_run.py `
  --run outputs/post_supplement/A_s5_10seeds `
  --config config/synthetic_main_s5_10seeds.json `
  --require-current-source `
  --report outputs/post_supplement/audit/A_s5_validation.json
```

A fully successful fresh run should report values including:

```json
{
  "status": "verified",
  "attempted_cells": 70,
  "status_counts": {
    "success": 70
  },
  "source_matches_current": true,
  "test_summary_recomputed": true
}
```

The verifier still accepts a completed run containing recorded failures, but all failed cells must remain present with terminal statuses and no replacement seeds.

### 6. Recommended order

Run the tasks in this order:

```text
thread settings
  -> preflight checks
  -> Task B summary
  -> Task C block 10/20/40
  -> Task C combine/verify
  -> Task A ten-seed benchmark
  -> Task A verification
```

This completes and checks the lightweight tasks before starting the expensive ten-seed benchmark.
